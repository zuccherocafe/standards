# Review rubric

Review every change to a zucchero✿café project with these questions, whoever wrote it. Tools run the lints and project checks, and these questions cover what tools cannot check. Answer each question with **pass**, **not applicable**, or a **finding**. In each finding, cite the supporting rule in [general.md](general.md) or in the language standard under [languages/rust/](languages/rust/), [languages/gdscript/](languages/gdscript/), or [languages/python/](languages/python/). The cited rule must be the most specific one that covers the finding. Cite a broad rule, such as [Correctness comes from the design first](general.md#design) or [Keep the system coherent](general.md#design), only when no narrower rule covers it. Mark each finding as **must-fix** or **should-fix**, as the [change-review](../skills/change-review/SKILL.md) skill defines. Before landing, the change that introduced a must-fix finding must fix it, and must apply or decline with a reason each should-fix finding. Prefer a type to a run-time check unless the type costs more than the harm ([Correctness comes from the design first](general.md#design)), and never re-check what a type already proves.

## First

Answer these questions before the rest. The first three ask whether the change fits what the project already has, and the fourth weighs every finding the review makes. A must-fix finding under any of them means the change is not ready, however well it answers the others. The [concord](../skills/concord/SKILL.md) skill covers the read of an area's models, overlaps, and transitions.

1. **One home.** Does each concept the change touches have exactly one home, or does the change add a second way that overlaps one the project already has? Is a new representation justified by a genuinely different form, with one explicit conversion? ([Keep the system coherent](general.md#design), [One home per concept](general.md#design))
2. **Transitions.** Does the change finish every transition it starts, leaving no old path beside the new one? Does it build on a transition an earlier change left unfinished? Does it serve the planned work that will touch it next? Where the area's concord note records disagreements, did the change weigh settling nearby ones against the extra work? For every deleted or edited disagreement row in `docs/concord/`, does the code support the change, and does each unsettled disagreement remain recorded here or in its owning area's note? ([Keep the system coherent](general.md#design), [Design for where the system is going](general.md#design), [Keep the concord note current](../skills/concord/SKILL.md#keep-the-concord-note-current))
3. **Repetition.** Does a changed document, rule, or skill repeat another, or should two passages or files be one? In the finding, name the consolidation. ([One home per concept](general.md#design))
4. **Worth fixing.** For each finding, who can produce the input that reaches it, what would a person see, and what does the fix cost? Accepting the risk is one of the answers. ([Weigh each fix, then fix the cause](general.md#design))

## General

1. **Invalid states.** Can a new type, field, parameter, or return value hold a forbidden domain value? Can individually valid inputs produce an inapplicable or non-finite result without a named outcome? ([Make invalid states unrepresentable](general.md#design))
2. **Correct.** Does every real input get the right answer, not only tested inputs? Does every input inside a function's stated contract get the right answer, even one nothing passes today? Does the code refuse every other input, or fail loudly, rather than give a silently wrong result? Are generated results reused only while every input that shaped them is unchanged? ([Correctness comes from the design first](general.md#design), [Generated output is typed and trusted](general.md#design))
3. **Boundaries.** Does anything re-check a value past its parsing boundary? If a check was removed, does a type make its failure impossible, or does evidence show that real data cannot reach it? Does every refusal of an author's mistake name the file, line, and field? ([Parse at the boundary](general.md#design))
4. **Knowledge as data.** Does general code now contain input-specific knowledge that belongs in the input's files, such as a name, mapping, or case? ([Knowledge is data](general.md#design))
5. **Who fixes each error.** Is each new failure the author's, the environment's, a reader program's, or ours? Does the code carry a bug as a refusal or treat an author's mistake as a bug?
6. **Written files.** Does every written file remain byte-equal? If not, does the change identify the difference and format tag? Does it update every reader in the same commit? ([Records](languages/rust/design.md#records))
7. **Scenarios and expectations.** Which scenario does the change touch? Does a test reach the changed code through its most common real use? Was every expected value hand-written or, for exact text or structured output whose shape is the promise, accepted as a reviewed snapshot? Is any test kept for an input nothing real produces? Could each test fail if the code were wrong, or does it recompute the answer the code's way, call the code for its expected value, or assert only that it ran? Was any visibility, accessor, parameter, hook, or trait added only for a test? Does any scenario in the checks take more than seconds? Does any property test use a fresh seed or write a file? ([Checks](general.md#checks), [Traits](languages/rust/design.md#traits), [The test policy](languages/rust/tests.md#the-test-policy), [Properties](languages/rust/tests.md#properties))
8. **Checks.** Does the change add or widen a check above a unit test? If so, does it state the failure caught, why unit tests cannot catch it, and the added running time? Has the maintainer approved it? Does it fail on a difference rather than a broken result? Does it fail on a measurement that varies from run to run, such as a timing, rather than report it? Does a result that is only sometimes broken, such as an occasional non-finite value, still fail? ([Checks](general.md#checks))
9. **Simplicity.** Is there a simpler shape, within the change's concept, that is still correct and worth the rework? Is there validation, a refusal, a type, or a test that nothing real needs? Is anything simpler at the cost of being wrong for an input that must get the right answer? ([Simplify, never at the cost of correctness](general.md#design))
10. **Comments and documentation.** Does a comment state what a type could enforce? Does a configuration file carry instructions or placeholders from a template, or comments on obvious values? Does any text narrate history or describe a former state? Does documentation name a tool or library version outside the documentation rule's exceptions, or keep a changing inventory? Does each module explain its design in its own documentation? Is every public item documented, rather than explained only in a distant specification? Does the change's prose (documentation, comments, descriptions, messages) follow the writing rules? ([Writing](general.md#writing))
11. **Performance.** Does the change touch a hot path? If so, does it report before-and-after cost using a measure unaffected by unrelated machine activity? Is any budget exceeded? Does a claim of faster or free state what was measured? ([Performance](general.md#performance))
12. **Toolchain.** Is a new tool or changed version added to the development shell in the same change as its version check? Is it pinned by exact version and hash? Is a GPU program the publisher's unchanged binary? Is any toolchain more than three months behind? Does an upgrade move one toolchain with the pins coupled to it and nothing else, fix every site a new lint reports, and carry the full checks and a dandegate report? ([Toolchain](general.md#toolchain))
13. **Commit messages.** Does each subject name one scope and say what the commit does in the imperative, within about 72 characters, or state old and new versions for a pin? Does each commit that is not trivial have a body that says why, what the diff hides, and what was left out, standing on its own? ([Version control](general.md#version-control))

## Rust

1. **Wrong owner.** Can an identity, index, or checked value be used with the wrong collection, instance, or source? ([Identities](languages/rust/design.md#identities), [Index spaces](languages/rust/design.md#index-spaces), [Checked against a source](languages/rust/design.md#checked-against-a-source))
2. **Invariants on every path.** Does every construction or mutation preserve an invariant type's invariant? Check constructors, `Deserialize`, `Default`, mutators, conversions, and `pub(crate)` fields. ([Invariants](languages/rust/design.md#invariants), [Deserialising](languages/rust/design.md#deserialising))
3. **Numbers.** Is a quantity a bare `f64` in a crate-level interface ([Identities](languages/rust/design.md#identities))? The report scans identify quantities with unit-bearing names. Can finite inputs overflow or lose definition without a check? Does an `as` cast lack its bound? ([Quantities](languages/rust/design.md#quantities), [The numerical contract](languages/rust/design.md#the-numerical-contract))
4. **Shapes of state.** Does a `bool` mode, sentinel, enum-related `Option`, or set of parallel vectors need a sum type? Does a new project-enum variant fail to compile where it needs a decision? Outside a numerical kernel's working pairs, does a same-typed tuple in a domain or interface value carry meaning through order? Are bare primitive types used beyond temporary numerical arithmetic, in stored state, behind private invariants, or in crate-level interfaces? ([Sum types](languages/rust/design.md#sum-types), [Closed sets](languages/rust/design.md#closed-sets), [Tuples](languages/rust/design.md#tuples), [Quantities](languages/rust/design.md#quantities))
5. **Public API.** Where the brief picked the public API report, read it first. Is anything public that no other crate uses? Is any field public whose type admits invalid values? Is tuning exported as an input? ([Visibility](languages/rust/design.md#visibility))
6. **Records.** Does a working input derive serde? Does a genuinely different wire form justify a new wire type? Is there one conversion and a round-trip test against a hand-written fixture? Does `Debug` reach a record, identity, or key? ([Records](languages/rust/design.md#records), [Debug](languages/rust/design.md#debug))
7. **Errors.** Is there one error per operation, with context attached once by the layer that knows it? Does a `Display` repeat its source or contain a code? Does panic behaviour match the crate kind? Is every moved refusal listed? Does a moved refusal still refuse every input it refused before? Does any test fix the order of independent faults? ([Errors](languages/rust/errors.md#errors), [Where a refusal sits](languages/rust/errors.md#where-a-refusal-sits))
8. **Purity.** Does a core now read a file, the clock, the environment, or a process? Inside a shell crate, is new logic a named function over values with input and output at the boundaries? ([Purity](languages/rust/design.md#purity))
9. **Lifetimes and traits.** Does a new lifetime bind a view to its source or merely bundle arguments? Does a new trait have several implementations? Does it invert a dependency the core must not have? ([Lifetimes](languages/rust/design.md#lifetimes), [Traits](languages/rust/design.md#traits))
10. **Rule-shaped code.** Does a rule force a trait, type, or module that a strong Rust engineer would reject as unnecessary for the domain?
11. **The better shape.** What design would a strong Rust engineer choose here, at this project's scale? Why does the proposed design differ, and what would moving to it cost? Answer in prose. A finding that asks to replace a dependency or redesign a module is must-fix only when a real input gives a wrong result or a stated promise breaks without it, as [change-review](../skills/change-review/SKILL.md) classifies findings.
12. **Hot paths.** Does per-frame or per-item code on a real-time or engine path allocate once prepared for repeated use? Does it clone to satisfy the borrow checker? Does it grow collections incrementally despite a known size? Does a type added to a hot path have before-and-after instruction counts? ([Performance](languages/rust/performance.md#performance))
13. **Surviving mutants.** Where the brief picked a mutation report, does it list every mutant the tests missed? Is each missed mutant judged as a real gap with its test added, an equivalent mutant with its reason, or an unstated edge whose rule, where a reader depends on it, the documentation now states and a test checks? Is a timed-out mutant diagnosed rather than answered with a test? Was any test written only to catch a mutant? ([Mutation report](languages/rust/tests.md#mutation-report))
14. **Async.** Does a core await, import a runtime, or block? Does every spawned task have an owner that joins it? Is each `select!`, timeout, and abort reviewed for what it drops? Where an effect may already have happened, does a timeout or lost acknowledgement report an unknown outcome rather than a failure, and is known non-execution reported as such? Does every queue have a bound, a full policy, and a closed policy? Does shutdown follow dependency order? ([Async and concurrency](languages/rust/async.md#async-and-concurrency))
15. **Idiom.** Read the change as an experienced Rust reviewer would. Name each place, by file and line, where they would write it differently: tests in a separate file that belong beside their subject, an index loop an iterator states more plainly, a needless clone or allocation, a hand-written loop or helper the standard library or a dependency already provides, `Option` and `Result` handled by matching where a combinator or `?` reads better, a module split or name that hides what the code does. Each is a should-fix finding.

## GDScript

1. **Types.** Does a typed declaration from `Variant` lack a preceding `is` test? Do functions pass a dictionary where a record belongs, read it by dot access, or leave it untyped where a typed map fits? Does a sentinel represent absence? ([Typed everything](languages/gdscript/design.md#typed-everything), [A record is a class](languages/gdscript/design.md#a-record-is-a-class))
2. **Closed sets.** Does a string or integer represent a closed set? Does a `match` on the project's enum omit a member or an asserting default arm? Does an enum variable lack an explicit default? Does a reported name come from reflection rather than a map? ([Closed sets](languages/gdscript/design.md#closed-sets))
3. **Invariants.** Can a caller break a class's invariant by writing a field, or build it without its static constructor? ([Invariants](languages/gdscript/design.md#invariants))
4. **Boundaries.** Does a raw `Variant` or `Dictionary` leave its parser for a consumer? Does the code trust a typed export to validate a hand-written file? Does it load any external resource? Does it use a JSON number as `int` without conversion? Does it mutate a shared resource without a copy? Does it assume a deep copy isolates external sub-resources? ([Parsing at boundaries](languages/gdscript/design.md#parsing-at-boundaries))
5. **Errors.** Does a library function log and return `null`? Does the code carry a refusal as a `Variant` or print it instead of returning it? Does it use `assert` on input or drop an engine `Error`? ([Errors](languages/gdscript/errors.md#errors))
6. **Warnings.** Does each new `@warning_ignore` cover one warning on one statement? Does its reason name a constraint the code cannot show? Does the warning rule include each new project-owned addon? Does an engine upgrade set every new warning? ([Exceptions to a warning](languages/gdscript/warnings.md#exceptions-to-a-warning), [Include the project's own addons](languages/gdscript/warnings.md#include-the-projects-own-addons), [An engine upgrade reviews the warning list](languages/gdscript/warnings.md#an-engine-upgrade-reviews-the-warning-list))
7. **By name.** Does the code reach a method, property, or signal by name where the type is known? ([No duck typing](languages/gdscript/organisation.md#no-duck-typing))
8. **Lifetime.** Who frees each new node? Does the code free it with `queue_free`? After `await`, does a coroutine check the objects it uses? Does it await only objects that outlive it? Does a detached coroutine name its owner? Does a worker access the tree or finish without being joined? Does a static variable have an owner that resets it? Does a static initialiser require the running game? Does opening a `@tool` script cause writes? ([Lifetime, concurrency, and the editor](languages/gdscript/lifetime.md#lifetime-concurrency-and-the-editor))
9. **Hot paths.** Does per-frame code allocate, look up nodes by path, or read dictionaries? ([Performance](languages/gdscript/performance.md#performance))
10. **The better shape.** What would a strong Godot engineer write here, at this project's scale? Why does the proposed design differ, and what would moving to it cost? Answer in prose. A finding that asks to replace a dependency or redesign a module is must-fix only when a real input gives a wrong result or a stated promise breaks without it, as [change-review](../skills/change-review/SKILL.md) classifies findings.
11. **Idiom.** Read the change as an experienced Godot engineer would. Name each place, by file and line, where they would write it differently: a loop a built-in or a typed array method states more plainly, a signal or node lookup done by hand where the engine provides it, a helper that duplicates one elsewhere in the project, a name that hides what the code does. Each is a should-fix finding.

How an agent runs a review, and how fixes are checked and landed, is in the [change-review](../skills/change-review/SKILL.md) and [change-land](../skills/change-land/SKILL.md) skills.

## Python

1. **Types.** Does every function carry full type annotations? Does `Any` or an unchecked `object` reach past a parser or a host module's wrapper? Do functions pass a `dict` or tuple where a dataclass belongs? Can a caller construct or change a record with an invariant without checking it? Does a string represent a closed set rather than an `Enum`, or does a `match` over one omit `assert_never`? ([Types and records](languages/python/README.md#types-and-records))
2. **Boundaries.** Is text from a file, argument, environment, or process parsed into records once, where it is read, with refusals naming the file, line, and field? ([Parsing at boundaries](languages/python/README.md#parsing-at-boundaries))
3. **Entry point and errors.** Does work run at import time, beyond the import-path line? Does anything catch `Exception` and carry on, or print and continue? Does the code use `assert` on input? Does a subprocess use `shell=True`, or does its failure go unhandled? Does a tool write outside the folder it was given? ([Errors and the entry point](languages/python/README.md#errors-and-the-entry-point))
4. **Tests.** Do a tool's tests live in `test_<tool>.py` in its folder's `tests/`? Does a standalone tool's test go through `main` with a made-up input? Did the author write expected values by hand? Did the change add a parameter or hook to production code only for a test? Does code that needs a host keep its decisions testable without it? ([Tests](languages/python/README.md#tests))
5. **Exceptions.** Does each `noqa` or ignore cover one rule on one line with its reason? ([Exceptions to a check](languages/python/README.md#exceptions-to-a-check))
6. **Idiom.** Read the change as an experienced Python reviewer would, against [Idiom](languages/python/README.md#idiom). Name each place, by file and line, where they would write it differently: a loop a comprehension or the standard library states more plainly, `os.path` where `pathlib` fits, a hand-written helper the standard library provides, a name that hides what the code does. Each is a should-fix finding.
