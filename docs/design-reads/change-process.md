## Models in play

- A brief: `templates/BRIEF.md` defines it. It has a `Size.` field with the values `small`, `normal` and `design`. `design` means the change adds or changes a format, type, API or dependency, and a `design` brief links its read. `Decided.` lists each decision with "the document that records it". "Questions the writer settles" says the writer records each choice and its reason, but not where.
- A read: `templates/DESIGN-READ.md` and `skills/design-read/SKILL.md` define it as one file per read. Its header holds Area, Revision, Previous and Inspected. It has an `**Answer.**` paragraph, a `## After the last phase` section, a seven-column table with ID and Status, and four prose sections. Reads form a chain: each one carries forward the rows the previous read left open, and "Do not edit an earlier read after its phase lands" (`## Record the after-phase note in the next read`). Nothing says where reads are kept. The tool's fixtures use `<name>/design-read.md`.
- The check: `tools/crates/design-read` is the format's stated reference (`src/main.rs` module docs). It parses the header (`read.rs` `header`), checks the after-note against `Previous` (`after_note`), checks the table (`table`, `row`, `COLUMNS`, `RowId`, `Status`) and checks the carry-forward against the previous file (`carry.rs` `refusals`, `main.rs` `previous_rows`, `read.rs` `rows_of`). Its output counts rows by status (`Read::summary`). It checks one file per call (`Command::Check`).
- When a read is due: the triggers are "a phase" and "a design-sized brief" (format, type, API, dependency). Neither is a coherence trigger.
- A review: `change-review` reviews one change and mentions the brief review in one clause of step 1. `rules/review.md` First asks the coherence questions. The brief review itself has no procedure anywhere. `BRIEF.md` `Size.` says `small` "needs no brief review", and the design-read skill's `## Sample the area in a brief review` gives the only steps.
- A decision: `Decided.` items, "recorded decisions" and "named decisions" in `change-review`, and the writer's settled choices. Those choices go into the writer's report (`change-write` `## Write the report`), which is private. `general.md` "Write scoped, imperative commit messages" already asks for the why in a commit body that stands without private documents. "Documentation lives beside what it documents" already asks for a design's reasons in module docs.
- Landing: `change-land` fast-forwards the writer's branch and never writes code. A rebase conflict is resolved only when it is mechanical; otherwise the coordinator stops and asks.

## Overlaps

- The read trigger is stated six times in four wordings: `general.md` "Keep the system coherent" ("Before a new phase of work"), the `review.md` First intro, `BRIEF.md` `Size.`, the design-read skill's description and `## When a read is due`, `change-write` `## Before you write code` step 1, and `change-review` `## Read the brief, evidence, and diff` step 1.
- The definition of design size (format, type, API, dependency) appears in `BRIEF.md` `Size.`, design-read `## When a read is due` and `change-land` `## Decide what remains`.
- Three roles run `design-read check` on the same read: the coordinator before dispatch (`## Check before dispatching a writer`), the brief reviewer (`## Sample the area in a brief review`), and the writer, who stops if it fails (`change-write` step 1).
- The design-read skill says "does not read the code" twice, under `## What design-read check checks` and `## What stays human judgement`; `main.rs` module docs say it a third time.
- `review.md` asks the One home question twice, as First question 1 and General question 3, both citing the same rule.
- Where a reason goes is spread across `general.md` (commit body, docs beside the code), `BRIEF.md` (Questions) and `change-write` (report).

## Half-done transitions

- The chain of dated reads (Previous, carry-forward, Status) is fully built in the tool and skill, while the living per-area file replaces it. `carry.rs`, `Previous`, `rows_of`, `after_note`, `previous_rows`, the `previous/`, `mm4/` and `mm5/` fixtures, and the refused fixtures `after-*`, `previous-*`, `new-for-carried-id`, `carried-status-for-new-id`, `unresolved-id-omitted`, `unqualified-id`, `unknown-status`, `repeated-id` and `short-revision` exist only for the old model, with the scenarios in `tests/scenarios.rs` that use them.
- "Phase" is the planning unit in `general.md`, the template (`**Answer.**`, `## After the last phase`, `## What later phases need`, the Owner placeholder) and the skill. No inspected file defines a phase.

## What later work needs

- A brief's `Design read: <path>` must resolve on some revision. The read is the branch's first commit, but `change-write` follows only the `Do` list, and `BRIEF.md` `Do` has no read commit; the skill or the brief must say who makes that commit.
- A check over the whole folder needs a rule for `docs/design-reads/README.md`, which is not parsed. `check <file>` takes one file today.
- Concept uniqueness needs a refusal; nothing checks Concepts today.
- `templates/AGENTS.md` names no `docs/design-reads/` folder, and its Skills list has no design-read entry.
- The tool's dependencies and package name do not change.
