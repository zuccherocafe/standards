## Models in play

- A task is a Harbor task folder under `evals/tasks/<name>/`, in the shape of Harbor's `deepswe_tomlkit-toml-table-converters` example: `task.toml`, `instruction.md`, `environment/`, `tests/`, `solution/` and `shortcuts/`. Its starting tree is `tools/` of a reviewed revision that was never published. `environment/Dockerfile` rebuilds it from a public base on `main` and `environment/start.patch`, checks it against the tree id `task.toml` records as `source_tree`, and copies only that tree into the image, where one commit with fixed dates, `starting_commit`, holds it with no history. The image also prefetches the crates and the pinned toolchain, so every documented command works offline.
- The task's operating instructions are `environment/AGENTS.md`, committed in the starting tree, so pi loads them as `/app/AGENTS.md` in both conditions. They give the build and test commands, say what the container lacks, and tell the agent to skip any guide's steps that need it.
- The reference solution is `solution/solution.patch`, the production part of the landed correction at `solution_revision`, which `solution/solve.sh` applies for Harbor's oracle agent. `shortcuts/` holds the obvious wrong answers, each of which must score 0.
- The treatment is the standards guidance bundle: `rules/`, `skills/`, `templates/`, `README.md`, `CONTRIBUTING.md` and `LICENSE` at one revision of this repository, extracted into `.cache/evals/standards-<revision>/` and mounted read-only at `/root/.agents`, with `evals/treatment/AGENTS.md` mounted read-only as pi's user context file, `/root/.pi/agent/AGENTS.md`. `evals/configs/treatment.yaml` holds both mounts and is layered after the control's configuration; since Harbor replaces a layered configuration's mount list rather than adding to it, it also repeats `pi.yaml`'s settings mount. The bundle leaves out `tools/` and `docs/`, because they hold the tasks' answers. The control has no standards bundle and no inherited user guidance; it differs from the treatment only in these mounts, apart from what each trial's own installation of pi brings (below).
- The agent's installation: Harbor 0.24.0's pi agent installs nvm v0.40.2, the newest Node 22 and pi through npm in every trial, during setup, from `raw.githubusercontent.com`, `nodejs.org` and the npm registry. It has no way to reuse an installation the image already holds. The pi version is pinned; Node's patch release and every package below pi are whatever those hosts serve that day. A collect hook records the installed Node, npm and pi versions and the npm tree as `/var/tmp/agent-identity.txt`.
- pi's settings: `evals/configs/pi-settings.json`, mounted read-only in both conditions as pi's user settings, turns compaction and cache warming off and keeps pi's own retry of a failed request, one initial attempt plus up to three retries, with provider-level retries off.
- pi's context: pi 1.4.0 builds its system prompt from the context files in its agent folder and in the working folder and its parents, and lists the name, description and path of each skill it finds under `~/.agents/skills`, without the skill's text, which the model reads when it needs it. Neither needs project trust. A skill whose frontmatter sets `disable-model-invocation` is not listed.
- The network: each task's environment, and its agent phase, allow only `openrouter.ai`, so nothing after the agent's run, such as the collect hooks, restores wider access. Harbor's Podman backend enforces both, and the verifier's `no-network`, through an egress sidecar it builds from `environments/docker/harbor-docker-egress-control-sidecar/`.
- The verifier is a separate environment, a fresh container of the task's image with no network, started after the agent's container stops. A collect hook in `task.toml` writes the agent's change, `git diff --cached --binary <starting_commit>` after `git add -A`, to `/var/tmp/model.patch` in the agent's container once the agent phase ends; Harbor collects that artifact and restores it in the verifier, which never sees the agent's filesystem. `tests/test.sh` applies the change, then `tests/test.patch`, checks with `cargo metadata` that the hidden tests' target is still the crate's own integration test at its own path, runs the crate's existing tests, then runs the hidden tests by naming that target, and scores 1 only when the existing tests pass and every hidden test, by its authored count, ran and passed. It writes each stage's result beside the score in `reward.json`.
- Trial identity: Harbor's `config.json` and `lock.json` for the job (task digests, agent, version and model) and `result.json` for each trial; the standards revision is in the bundle folder's name in the treatment mount; the task's source revisions are in `task.toml`'s metadata; the agent's installation is in each trial's `agent-identity.txt`.
- Accounting: pi stores each assistant response with the id of the provider's response, taken from its first streamed chunk, and its stop reason. OpenRouter's generation record for that id is the source of the request's tokens (`native_tokens_prompt`, `native_tokens_cached`, `native_tokens_completion`, `native_tokens_reasoning`) and its charge (`total_cost`). `evals/README.md` gives the commands that fetch the record for every recorded request, keep the queried id and each field as given or mark it absent, keep a request's token counts when its charge is unavailable, and count a request with no record as unreported, never as zero. pi writes a response's row when the response ends, so the rows cover the requests pi recorded, not every request sent.

## Overlaps

- Tokens and cost have three records. pi's session keeps a usage object per response, with fields pi sets to zero before the response arrives and when the provider omits them, and a cost from pi's bundled prices. Harbor's `result.json` sums pi's input, cache reads and cache writes into `n_input_tokens` and copies pi's cost into `cost_usd`. OpenRouter's generation record keeps what the provider reported and what was charged. The evals report only the third.
- The starting tree has two homes, the reviewed revision in this repository's history and the base plus `start.patch`; the Dockerfile's tree-id check ties them.

## Half-done transitions

- Harbor 0.24.0 still collects `/logs/artifacts/` automatically and documents that it will stop; the tasks declare their artifacts explicitly, outside that folder, so they do not depend on either behaviour.

## What later work needs

- The smoke run and the pilot reuse the outcome categories (the stages in `reward.json`, and Harbor's exception for a trial that never reached the verifier), the per-request charge rows, the cost method (charged cost by response id, otherwise an estimate from a dated price source), and the identity fields above. Before the pilot, the smoke run must produce, for each model, the generation records of its requests beside the provider's own usage for the same responses as pi received them, so that the meaning of `native_tokens_prompt` and `native_tokens_cached` is established from both rather than assumed, and the key's charges for the run beside the recorded requests, so that any charge without a recorded request shows. Neither establishes OpenRouter's billing policy for requests that fail before their first chunk; only OpenRouter's documentation or a reconciliation of every charge can.
- Later task sets, including a private one for tdollhouse, reuse the task layout, the verifier's stages and the treatment mounts; a task whose answer lies outside `tools/` lets the bundle carry `tools/` too.
