## Models in play

- A task is a Harbor task folder under `evals/tasks/<name>/`, in the shape of Harbor's `deepswe_tomlkit-toml-table-converters` example: `task.toml`, `instruction.md`, `environment/`, `tests/`, `solution/` and `shortcuts/`. Its starting tree is `tools/` of a reviewed revision that was never published. `environment/Dockerfile` rebuilds it from a public base on `main` and `environment/start.patch`, checks it against the tree id `task.toml` records as `source_tree`, and copies only that tree into the image, where one commit with fixed dates, `starting_commit`, holds it with no history. The image also prefetches the crates and the pinned toolchain, so every documented command works offline.
- The task's operating instructions are `environment/AGENTS.md`, committed in the starting tree, so pi loads them as `/app/AGENTS.md` in both conditions. They give the build and test commands, say what the container lacks, and tell the agent to skip any guide's steps that need it.
- The reference solution is `solution/solution.patch`, the production part of the landed correction at `solution_revision`, which `solution/solve.sh` applies for Harbor's oracle agent. `shortcuts/` holds the obvious wrong answers, each of which must score 0.
- The treatment is the standards guidance bundle: `rules/`, `skills/`, `templates/`, `README.md`, `CONTRIBUTING.md` and `LICENSE` at one revision of this repository, extracted into `.cache/evals/standards-<revision>/` and mounted read-only at `/root/.agents`, with `evals/treatment/AGENTS.md` mounted read-only as pi's user context file, `/root/.pi/agent/AGENTS.md`. `evals/configs/treatment.yaml` holds both mounts and is layered after the control's configuration; since Harbor replaces a layered configuration's mount list rather than adding to it, it also repeats `pi.yaml`'s settings mount. The bundle leaves out `tools/` and `docs/`, because they hold the tasks' answers. The control has no standards bundle and no inherited user guidance; it differs from the treatment only in these mounts.
- The agent's installation: every task image holds Node and pi, installed when the image builds by `evals/pi/install.sh`, which takes the Node release it names, checked against its SHA-256, and pi 1.4.0 with its whole dependency tree from `evals/pi/package-lock.json`, with npm's install scripts off. Each task's `environment/docker-compose.yaml` builds its image from `evals/` rather than from the task's folder, so the one copy in `evals/pi/` serves every task; `evals/.dockerignore` admits only the files the Dockerfiles copy, so no hidden test, reference solution or shortcut, nor any file a later task adds outside them, enters a build. Harbor 0.24.0's pi agent would install nvm, the newest Node 22 and pi through npm in every trial; the development shell's Harbor carries `evals/harbor/pi-installed.patch`, which replaces that installation with a check of the image: its `install` does nothing when the image has pi on `PATH` at the configured version, and refuses the trial, naming the version to rebuild with, when the image has another version or no working pi. Setup therefore needs no network, and a Harbor whose module no longer takes the patch exactly fails the shell's build. A collect hook records the image's Node, npm and pi versions, the lockfile's digest and pi's installed tree as `/var/tmp/agent-identity.txt`.
- pi's settings: `evals/configs/pi-settings.json`, mounted read-only in both conditions as pi's user settings, turns compaction and cache warming off and keeps pi's own retry of a failed request, one initial attempt plus up to three retries, with provider-level retries off.
- pi's context: pi 1.4.0 builds its system prompt from the context files in its agent folder and in the working folder and its parents, and lists the name, description and path of each skill it finds under `~/.agents/skills`, without the skill's text, which the model reads when it needs it. Neither needs project trust. A skill whose frontmatter sets `disable-model-invocation` is not listed.
- The network: each task's environment, and its agent phase, allow only `openrouter.ai`, so nothing after the agent's run, such as the collect hooks, restores wider access. Harbor's Podman backend enforces both, and the verifier's `no-network`, through an egress sidecar it builds from `environments/docker/harbor-docker-egress-control-sidecar/`. The development shell's packaging keeps the sidecar scripts' `#!/bin/sh`, which the Nix build would otherwise point into its store, and wraps Harbor's commands so that their own Podman calls read `evals/registries.conf`, through `CONTAINERS_REGISTRIES_CONF`, in place of the host's registries settings; its one alias resolves the sidecar's base image name `gogost/gost` to Docker Hub, and every image keeps its digest pin. `evals/harbor/egress-sidecar.patch` narrows the sidecar for every task and review: DNS checked before any NAT or local exemption, name lookups only as single A or AAAA questions for names the allowlist holds exactly, in any case, ICMP only as errors about tracked traffic and link-scoped neighbour discovery, and no raw-socket or network-administration power in the task's containers. Exact-name DNS queries still carry caller-selected IDs, letter case, RD/AD flags, A/AAAA selection and, when present, EDNS size, extended-RCODE, version and flag fields; the filter does not normalise these fields or guarantee what the resolver forwards, so a residual DNS signalling channel remains and this is not a zero-egress boundary. On a handled exit, the sidecar attempts to empty the allowlist while retaining the rules, and logs whether that succeeded; abrupt termination can leave the previous allowlist rules in force. The wrapper also sets `PODMAN_COMPOSE_WARNING_LOGS=false`, since Podman's compose otherwise starts every command's output with a banner, which Harbor's Codex agent reads as its version.
- The verifier is a separate environment, a fresh container of the task's image with no network, started after the agent's container stops. A collect hook in `task.toml` writes the agent's change, `git diff --cached --binary <starting_commit>` after `git add -A`, to `/var/tmp/model.patch` in the agent's container once the agent phase ends; Harbor collects that artifact and restores it in the verifier, which never sees the agent's filesystem. `tests/test.sh` applies the change, then `tests/test.patch`, checks with `cargo metadata` that the hidden tests' target is still the crate's own integration test at its own path, runs the crate's existing tests, then runs the hidden tests by naming that target, and scores 1 only when the existing tests pass and every hidden test, by its authored count, ran and passed. It writes each stage's result beside the score in `reward.json`.
- Trial identity: Harbor's `config.json` and `lock.json` for the job (task digests, agent, version and model) and `result.json` for each trial; the standards revision is in the bundle folder's name in the treatment mount; the task's source revisions are in `task.toml`'s metadata; the agent's installation is in each trial's `agent-identity.txt`.
- Review: `evals/review/` holds the rubric, the evaluator's prompt, `blind.sh`, which makes the packets and keeps the key, and `results.sh`, which joins the verdicts with it; `evals/review/codex/` holds the Codex reviewer's image, its evaluator task's `task.toml`, `review.sh`, which runs the review, and `scan.sh`, which looks for the login in what it wrote. The run guide's [Reviewing each trial's change](../../evals/README.md#reviewing-each-trials-change) says how they fit and why.
- Accounting: pi stores each assistant response with the id of the provider's response, taken from its first streamed chunk, and its stop reason. For a model pi calls in OpenRouter's chat completions format, that id is OpenRouter's generation id, and OpenRouter's generation record for it is the source of the request's tokens (`native_tokens_prompt`, `native_tokens_cached`, `native_tokens_completion`, `native_tokens_reasoning`) and its charge (`total_cost`). The generation endpoint accepts only that form: OpenRouter's OpenAPI description requires an `id` matching `^gen-[0-9A-Za-z-]+$`. pi 1.4.0 calls a model whose entry in its OpenRouter model list (`pi-ai`'s `providers/data/openrouter.json`) names the `anthropic-messages` API, such as `anthropic/claude-opus-5.5`, through OpenRouter's Messages endpoint, and for a successful streamed response stores in `responseId` the `id` of the stream's `message_start` event, the upstream `msg_…` id. The endpoint documents no generation id in a successful response's events or headers, pi passes the response's headers only to extensions and records none, and OpenRouter's activity and analytics endpoints need a management key and describe totals by day, model or key rather than a lookup by message id. A request that fails with an HTTP error is different: OpenRouter's documented error body can carry a `gen-…` `request_id`, and Anthropic's SDK puts a body without a top-level `message` into the error's message, which pi stores as the response's `errorMessage`; whether that id can be looked up, or what it was charged, is unverified. So for such a model the recipe has no per-request or per-trial tokens or charges, and the key's charge in the reconciliation, for the whole run, is its account of record. The run guide's [Running](../../evals/README.md#running) and [Results](../../evals/README.md#results) sections give the commands that turn these records into rows and reconcile their sum with the key's charges, what that reporting leaves out, and its approval.

## Overlaps

- Tokens and cost have three records. pi's session keeps a usage object per response, with fields pi sets to zero before the response arrives and when the provider omits them, and a cost from pi's bundled prices. Harbor's `result.json` sums pi's input, cache reads and cache writes into `n_input_tokens` and copies pi's cost into `cost_usd`. OpenRouter's generation record keeps what the provider reported and what was charged. The evals report only the third, and for a model pi calls in Anthropic's Messages format, none of the three per request.
- The starting tree has two homes, the reviewed revision in this repository's history and the base plus `start.patch`; the Dockerfile's tree-id check ties them.
- The standards the review judges by and the standards the treatment carries are one revision, the one `evals/configs/treatment.yaml` names, which `review/blind.sh` reads.
- Codex's version has two homes, the image's release in `evals/review/codex/Dockerfile` with its tag in `evals/review/codex/task.toml`, and the `version` the review command gives the agent; Harbor's Codex agent installs over the network when the image holds another version, which the evaluator's network refuses.
- pi's version has two homes, the pi agent's `version` in `evals/configs/pi.yaml` and `evals/pi/package.json` with its lockfile; the patched agent refuses a trial whose image holds another version than the configuration names.

## Half-done transitions

- Harbor 0.24.0 still collects `/logs/artifacts/` automatically and documents that it will stop; the tasks declare their artifacts explicitly, outside that folder, so they do not depend on either behaviour.

## What later work needs

- The smoke run and the pilot reuse the outcome categories (the stages in `reward.json`, and Harbor's exception for a trial that never reached the verifier), the per-request charge rows, the reporting method in the run guide's [Results](../../evals/README.md#results), and the identity fields above. Before the pilot, the smoke run must produce, for each model whose stored ids permit a generation lookup, the generation records of its requests beside the provider's own usage for the same responses as pi received them, so that the meaning of `native_tokens_prompt` and `native_tokens_cached` is established from both rather than assumed. That comparison is unavailable for a model pi calls in Anthropic's Messages format under the current integration, whose reduced reporting needs the approval the run guide's [Running](../../evals/README.md#running) describes. Each run's reconciliation shows spend missing from the summed charges, whether from a request without a row or a row whose charge is unavailable, but cannot say which request or trial it belongs to, so it does not establish OpenRouter's billing policy for requests that fail before their first chunk; only OpenRouter's documentation can.
- Later task sets, including a private one for tdollhouse, reuse the task layout, the verifier's stages and the treatment mounts; a task whose answer lies outside `tools/` lets the bundle carry `tools/` too.
